## Cross-Task Summary

### Side-effect tasks (mutate environment)
- **`check_new_reservation` (HOTEL only)**: UT0 only.
- **`check_new_event` (calendar+email, both required)**: UT1, UT4, UT7, UT8.
- **`check_new_email` (single email, no calendar)**: UT3.
- **Mutation tolerated, no explicit gate**: UT6 (utility omits `pre == post` and any check_new_* helper; mutations are silently allowed).

### Pure-read (pre == post) invariant tasks
UT2, UT5, UT9, UT10, UT11, UT12, UT13, UT14, UT15, UT16, UT17, UT18, UT19.

### Tasks that need calendar reads
None of UT0–UT19 actually CALL `get_day_calendar_events` or `search_calendar_events` in their ground_truth. The only calendar interaction is **writes** (`create_calendar_event` in UT1, UT4, UT7, UT8).

### Tasks that need email sending (`send_email`)
UT3 only. UT1, UT4, UT7, UT8 add an email indirectly via `create_calendar_event` (which auto-sends an invitation email — see `calendar_client.create_calendar_event` lines 161-167).

### Tasks that book reservations (`reserve_hotel`)
UT0 only. No travel user task uses `reserve_restaurant` or `reserve_car_rental` despite prompts that mention "rent a car" (UT13–UT16 use `get_*` only) or "book a flight" (UT16, which still only reads flight info).

### Tasks that need flight info
UT16 only (`get_flight_information(departure_city="Paris", arrival_city="London")`).

### DIFFICULTY declarations
- Explicit: UT0=EASY, UT1=EASY, UT2=MEDIUM, UT3=MEDIUM, UT4=MEDIUM, UT5=MEDIUM, UT6=HARD.
- Implicit default (EASY from `BaseUserTask.DIFFICULTY`): UT7–UT19 (13 tasks). **NOTABLE**: UT11, UT12, UT17, UT19 are clearly multi-step / multi-domain tasks comparable to UT6 (HARD) in complexity, yet they inherit `EASY` because no class-level `DIFFICULTY` is set.

### Date-year mismatch (utility uses `strftime("%m-%d")` to ignore year)
- **UT1**: prompt "January 2nd 2025" / ground truth `2025-01-02`. Year aligned (consistent).
- **UT4**: prompt "April 25th **2024**" / ground truth **`2023-04-25`** → mismatch, tolerated.
- **UT7**: prompt "the 14th of November" (no year) / ground truth `2023-11-14` → tolerated.
- **UT8**: prompt "October 15th" (no year) / ground truth `2023-10-15` → tolerated.
- This is a consistent upstream pattern: ground_truth dates default to 2023 even when prompt says 2024+. The utility silently accepts any year so long as month-day matches.

### Substring-matching looseness (high risk of false positives)
- Many checks use small numeric substrings: `"4.5"`, `"30"`, `"80"`, `"5"`, `"180"`, `"200"`, `"300"`, `"690"`, `"1080"`, `"3920"`.
- Worst offender: **UT3** `rating = "5"` (one-character substring; matches `"500"`, `"5000"`, address "75002", etc.).
- **UT11** has typo `hotel in model_output in model_output` — Python chained comparison `(hotel in model_output) and (model_output in model_output)`. Since a string trivially contains itself, the second `in` clause is constantly True and the typo is behaviorally inert.

### COMMENT vs PROMPT mismatches (cosmetic but notable)
- **UT13** COMMENT says "in Paris" but task is LA SUV search.
- **UT14** COMMENT says "in Paris" but task is LA electric.
- **UT16** COMMENT says "electric cars in London" but task is "best-rated".
- **UT18** COMMENT says "less than 100" but actual filter is `< 50`.

### Known oddities (per request)
- **UT4 / UT8**: PROMPT year vs ground_truth year mismatch (2024 vs 2023; "no year" vs 2023). Utility hides via `%m-%d` only — documented above.
- **UT12**: PROMPT requests "lunch and dinner" at a top-rated French restaurant, but the chosen Le Baratin closes Wed/Sun/Mon (only Tue/Thu/Fri/Sat) — prompt's Nov 15 (Wed if 2023, Fri if 2024) is half-broken; utility doesn't verify operating hours.
- **UT19**: London top-rated restaurant `"House of Sushi"` has `cuisine_type: "Italian"` in seed data — intentional/known data inconsistency that utility cannot detect because it only checks the name substring.

### Severity legend
- **CRITICAL** = utility passes for wrong answers / has logic that contradicts the prompt's hard constraints in a load-bearing way. **No tasks reach CRITICAL** in this audit (the worst pattern, UT12, has a near-CRITICAL discrepancy between prompt-day-of-week and operating-hours, but it's tolerable because the prompt's day constraint is implicit).
- **NOTABLE** = utility passes despite imperfect prompt-alignment, year mismatch, loose substring matches, missing DIFFICULTY declaration, or known data oddity. Applies to: **UT0, UT2, UT3, UT4, UT6, UT7, UT8, UT11, UT12, UT13, UT16, UT17, UT18, UT19**.
- **OK** = utility is straightforward, prompt-aligned, no anomalies beyond minor typos. Applies to: **UT1, UT5, UT9, UT10, UT14, UT15**.

### Key load-bearing code snippets
- **`check_new_event` constant** (line 23-26): `f"root.calendar.events['{next_event_id}']", f"root.inbox.emails['{next_email_id}']"` — both must appear at next sequential IDs. Any extra mutation (e.g., reservation) fails the check.
